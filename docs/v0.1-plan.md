# QCJudge V0.1 — working plan

Status: draft for review. This document is the working plan for reaching `v0.1.0`.
It records decisions, the audit workflow, the module map, the debt register, and the
milestone gates. `docs/architecture.md` states the durable architecture; this file states
where we are, what is missing, and in what order to close it.

> **Handing this project to a new agent?** Read [`docs/handoff.md`](handoff.md) first. It is the
> measurement of where the project actually stands, what is blocked and why, and the traps that are
> easy to reintroduce. Come back here for the debt register and the milestone gates.

Nothing here changes the scientific epistemics already fixed in `docs/scientific-scope.md`.

## 2. Positioning, restated as a boundary

QCJudge answers one question: given a stated scientific question, do the available
computational results constitute appropriate and sufficient evidence for it? It does not
answer "did the job run" and it does not answer "is the conclusion true".

Explicit non-overlap. We do not reimplement, and should not be described as:

- natural-language workflow planning or autonomous computational agents (ChemGraph-like);
- execution environments, HPC orchestration, job submission, input generation;
- wavefunction-analysis algorithms (Multiwfn and peers) — we *consume* their output;
- claim-level reproducibility benchmarks (AutoMat-like) — we audit prospective adequacy
  for a question the researcher already has, not retrospective reproducibility.

The README must keep this distinction visible; it currently does.

## 3. The audit workflow

Nine stages, each owned by exactly one layer. This is the spine of the project; every
module exists to serve one of these stages.

| # | Stage | Owner | Determinism |
| --- | --- | --- | --- |
| 1 | Research question | `domain/question.py` | user-supplied |
| 2 | Hypothesis | `domain/question.py` | user-supplied |
| 3 | Claims | `domain/question.py` + `protocols/` | protocol-declared |
| 4 | Evidence requirements | `protocols/` | declarations |
| 5 | Available calculations | `parsers/`, `adapters/` | deterministic |
| 6 | Extracted facts | `evidence/facts/` | deterministic |
| 7 | Validity checks | `validators/` | deterministic |
| 8 | Evidence mapping | `evidence/matching.py` | deterministic |
| 9 | Sufficiency assessment | `audit/` | deterministic |

Derived outputs — missing evidence, recommended next step, rendered explanation — are
projections of the stage-9 result, never new reasoning.

The invariant that defines the project: **a report may be `execution = PASS` and
`evidence = INSUFFICIENT` at the same time, and that is the normal, expected outcome for
a large fraction of real audits.** Stages 7 and 9 are computed on different axes and must
never be collapsed into one another.

## 4. Module map and dependency rules

```
cli/                    argparse only; no science, no formatting logic
render/                 text + json rendering of AuditReport
    text.py             human-readable report
    json_report.py      the stable machine-readable contract
audit/                  orchestration, aggregation, trace graph
    engine.py           orchestration only — contains no requirement or rule ids
    aggregation.py      requirement -> claim -> hypothesis -> overall
    trace.py            the inspectable why-chain
evidence/               stages 6 and 8
    matching.py         requirement -> evidence, honouring groups and dependencies
    derivation.py       facts -> evidence, at the strengths a protocol declares
    facts/projection.py Observation -> ExtractedFact (provenance-bearing)
parsers/                stage 5, observations and diagnostics only
    base.py             CalculationParser contract
    orca.py             the declared ORCA subset
validators/             stage 7
    registry.py         implementation_key -> rule callable
    collect.py          fact reading and absence explanation, shared by rules
    execution.py        convergence and completion
    methodology.py      consistency, sensitivity, expert-review boundaries
protocols/              stages 3 and 4 declarations
    v1.py               the three built-in protocols
domain/                 pure types; imports nothing from this project but qcjudge.errors
    common.py           epistemic kinds, provenance, UnavailableReason
    question.py         question, hypothesis, claim, assumptions, binding
    evidence.py         fact keys, evidence types, inventory, requirements, groups
    validation.py       scopes, statuses, RuleOutcome, rule specs
    assessment.py       requirement, claim, and hypothesis assessments
    protocol.py         the versioned protocol object and dependency ordering
    audit.py            the self-contained report and trace edges
    context.py          the read-only context handed to rules and matchers
```

Enforced by `tests/test_layering.py`, which parses every source file rather than importing
it. Dependency direction is strictly inward:

- `domain` imports only the standard library and `qcjudge.errors`;
- `protocols`, `parsers`, `adapters`, `validators`, `evidence` may import `domain`;
- `audit` may import `domain`, `protocols`, `evidence`, `validators`;
- `cli` may import anything below it;
- `render` may import `domain` only;
- **no core module may import `cli`, `render`, an LLM SDK, a web framework, or a numeric
  stack.** The denylist is explicit in the test, not a convention.

Three deliberate departures from the layout sketched in the original brief:

1. `render/` is split out of `cli/`, because rendering is where overclaiming risk lives.
2. `evidence/facts/` is separate, because "record -> provenance-bearing fact" is a real
   transformation with its own failure modes and must not hide inside a parser.
3. `EvidenceInventory` lives in `domain/evidence.py` rather than `evidence/inventory.py`,
   because `AuditReport` carries it and `domain` may not import `evidence`. Recorded as
   D-16.

Rejected alternative: a declarative rule DSL (YAML conditions). Rejected for V0.1 because
a condition language must itself be specified, versioned, tested, and explained to
contributors, and it forfeits static typing. The requirement graph is data; the *rules*
that interpret it are code. If third-party protocols become a goal, add a loader that
**compiles** YAML into these same typed objects — serialized protocols are never the
authoritative source.

## 5. Domain model, refined

The chain is three levels deep, because collapsing hypothesis and claim loses exactly the
nuance the project exists to express.

```
ResearchQuestion  (family, text, hypotheses, context)
  Hypothesis      (a proposition worth supporting; may be broad)
    Claim         (a narrower, evidence-checkable statement)
      EvidenceRequirement
        -> satisfied by Evidence -> which cites ExtractedFact -> which has Provenance
```

Changes proposed against the existing model:

**`Hypothesis` is added.** Today `audit()` takes a bare `QuestionFamily` and the report's
`question_text` is taken from the protocol's claim, so the user's own question never
appears. Adding the level also lets a report say "claim A supported, claim B unaddressed,
hypothesis therefore not established", which is the honest output.

**Alternatives become an explicit group.** `EvidenceRequirement.alternatives` is currently
a per-requirement cross-reference, declared twice (once in each direction) and enforced
nowhere. Replace with `EvidenceGroup(id, member_ids, satisfaction=ANY_ONE|ALL)`; a
requirement carries `group_id: str | None`. Symmetry becomes structural instead of a
convention. This is what makes the transition-state protocol's "imaginary-mode inspection
**or** IRC" logic actually work.

**Requirements gain fields the engine already needs and ignores:**
`minimum_directness` (the field exists as `EvidenceStrength`/`EvidenceDirectness` but is
never checked), `required_facts` (which fact names must be present before the requirement
can even be evaluated, which is how `INSUFFICIENT` is distinguished from `NOT_ASSESSABLE`),
and `insufficiency_conditions` (explicit, testable statements rather than prose).

**Facts get a registry and a subject.** `ExtractedFact.name` is a free string today.
Introduce `FactKey` constants (`orca.scf.converged`, `tddft.state.energy_ev`,
`orca.freq.imaginary_count`, ...) validated at protocol load, plus a `subject` field so a
fact is unambiguously about a state, a mode, or a calculation. Free strings turn typos
into silently "missing evidence", which is the failure mode we least want.

**Evidence records its origin.** `Evidence` gains `origin: PARSED | ADAPTER | USER_ASSERTION`
and keeps `fact_ids`. A user saying "I inspected the mode" is an assertion with no
provenance; it must be structurally distinguishable from a parsed result (decision Q2).

**`EvidenceRequirement`, `Evidence`, and `ExtractedFact` all keep provenance** — source file,
producer, producer version, source location, extraction time. Protocol version is recorded on
the report and on each assessment instead, because a fact is a property of the output file and
not of a protocol.

**`AuditReport` becomes self-contained.** It must carry the question, the protocol
reference, the `EvidenceInventory` (facts + evidence), validation results, assessments at
all three levels, recommendations, the trace edges, tool version, and generation time.
Today the report has none of these, so "inspect why" is impossible from the report alone —
which is a core promise of the project.

**Assessment statuses and their exact, testable definitions.** These are decisions, not
implementation details:

| Overall status | Fires when |
| --- | --- |
| `SUPPORTED` | every `REQUIRED` requirement is satisfied at or above its level; unmet `RECOMMENDED` items are reported as gaps but do not block |
| `PARTIALLY_SUPPORTED` | at least one `REQUIRED` satisfied, at least one unmet, none contradicted |
| `INSUFFICIENT` | evidence coverage is determinable and no `REQUIRED` requirement is satisfied — the required calculation was not provided |
| `CONTRADICTED` | available evidence contradicts a `REQUIRED` requirement |
| `NOT_ASSESSABLE` | required inputs cannot be read — truncated file, unsupported construct, unimplemented extraction; epistemic access failed |
| `REQUIRES_EXPERT_REVIEW` | a declared expert-review boundary was triggered and blocks a decisive status |

The report must name the rule that produced the status. No scalar score; the evidence
graph stays visible.

**`INSUFFICIENT` vs `NOT_ASSESSABLE` is the sharpest line in the system.** The former is a
claim about evidence coverage — the calculation was not provided. The latter is a claim
about epistemic access — we could not read what was provided. Conflating them either hides
a missing calculation or blames the user for a gap in our own parser.

The distinction is decided by the parser's `UnavailableReason` for each required fact, not
by the audit engine:

| Reason | Meaning | Requirement outcome |
| --- | --- | --- |
| value present | parsed, with provenance | evaluated normally |
| `NOT_PROVIDED` | file is complete and readable; the calculation was not run | `INSUFFICIENT` |
| `FILE_TRUNCATED` | output is incomplete or the job died mid-run | `NOT_ASSESSABLE` |
| `UNSUPPORTED_CONSTRUCT` | parser does not implement this output yet | `NOT_ASSESSABLE` |
| `AMBIGUOUS_MATCH` | several candidate values, none authoritative | `NOT_ASSESSABLE` + expert boundary |

Overall precedence, first match wins: `CONTRADICTED` > `NOT_ASSESSABLE` > `REQUIRES_EXPERT_REVIEW`
> `SUPPORTED` > `PARTIALLY_SUPPORTED` > `INSUFFICIENT`.

**Requirements carry a role, and it decides partial versus unsupported.** Identifying an
excited state is a *prerequisite* for discussing its character; the spatial redistribution
itself is the *substance*. So `PARTIALLY_SUPPORTED` requires at least one substantive
required requirement to have some admissible evidence, and `INSUFFICIENT` means no
substantive requirement does. Without that distinction, "energies only" would be reported as
partially supported when in fact the claim has not been addressed at all.

**Two kinds of rule reference, because a rule failure means two different things.**
`gating_rules` decide whether the inputs are usable: a failure there means we cannot judge,
and the requirement becomes `NOT_ASSESSABLE`. `contradicting_rules` decide whether the
evidence rules the requirement out: a failure there means `CONTRADICTED`, and an
inconclusive result there means `NOT_ASSESSABLE`. Zero imaginary frequencies are the case
that forces the distinction: that is a *successful* calculation of a minimum, not a failed
calculation, so it must not appear on the execution axis at all (see the three scopes in
section 6).

**Protocol version does not belong on facts:** a fact is a property of the output file, not
of a protocol. It belongs on the report and on each assessment, so that an audit run can be
reproduced even after a protocol is revised.

## 6. Deterministic / expert / LLM boundary

Validation carries three scopes, because the questions are different and merging them would
let one leak into another. `EXECUTION` asks only whether a calculation finished and produced
usable output. `STRUCTURE` asks what the computed object actually is. `METHODOLOGY` asks
whether the inputs are mutually consistent and stops at a warning or an expert boundary.

| Statement | Deterministic core | Expert review | LLM |
| --- | --- | --- | --- |
| Parse a value out of an output file | yes | - | no |
| SCF / optimization converged | yes | - | no |
| Count imaginary frequencies, once the parser has vouched for the mode list | yes | - | no |
| "this Hessian is first-order at this stationary point" | yes (bounded to the computed Hessian) | - | no |
| "the imaginary mode follows the proposed reaction coordinate" | no | yes, or IRC evidence | no |
| donor/acceptor partition choice | no | yes | no |
| numerical CT threshold (D, Sr, Lambda) | no — no universal cutoff is asserted | yes | no |
| "is this method adequate for this system" | warning only | yes | no |
| map evidence to requirements, compute coverage | yes | - | no |
| translate a free-form question into `ResearchQuestion` | proposal only | - | yes, then user confirms |

The mode-list guard is worth spelling out, because it is the one place where two mechanisms
protect the same number. The parser refuses to report a frequency count from a file that did
not end normally, and the rule treats a mismatch against an expected mode count as
incomplete when that count is available. Today only the first mechanism is live, because
deriving 3N-6 needs an atom count this parser does not read (D-22).
| explain a finished report in prose | - | - | yes, read-only |

**The LLM firewall, structurally enforced.** Two types exist: `ResearchQuestionDraft`
(producible by an LLM) and `ResearchQuestion` (constructible only by a deterministic
promotion function that validates family, claim coverage, and required context). The LLM
layer's entire surface is therefore `str -> ResearchQuestionDraft` and
`AuditReport -> str`. It cannot write into facts, validation results, or assessments,
because it never receives them as writable objects.

Consequences for the initial package: no LLM SDK dependency, no `import` of any provider
in the core, and a test asserting the core imports stay clean. The whole audit must remain
useful with the LLM layer deleted.

## 7. Protocol schema

Every protocol declares, at minimum: `id`, `version`, `question_family`, `hypotheses`,
`claims`, `requirements`, `evidence_groups`, `validation_rules` (with `implementation_key`
resolved through the validator registry), `recommendations`, `limitations`,
`insufficiency_conditions`, and `max_defensible_claim_strength` — the last one exists so
the renderer cannot phrase a conclusion more strongly than the structure supports.

### 7.1 Charge-transfer excitation

- Claims: the target state is identified and characterized; the excitation involves
  substantial donor-to-acceptor charge redistribution.
- `REQUIRED` target-state assignment; `REQUIRED` spatial redistribution
  (`hole_electron_analysis | nto_analysis | attachment_detachment_density`), depending on
  the assignment; `RECOMMENDED` method sensitivity (`method_comparison |
  range_separation_validation`).
- Insufficient when: energies or oscillator strengths alone are offered; a assignment
  exists but no quantitative descriptor was computed.
- Expert-review boundary: descriptor present but the donor/acceptor partition is
  ambiguous.
- Never asserted: any universal numerical cut-off for "CT character".

### 7.2 TADF potential

- Claims: the relevant singlet–triplet gap is small under the stated method; a
  spin-forbidden channel capable of repopulating the singlet is supported by evidence;
  the radiative channel is characterized (`RECOMMENDED`).
- `REQUIRED` singlet/triplet identification and gap; `REQUIRED` RISC-relevant evidence
  (`spin_orbit_coupling | risc_rate | vibronic_coupling_analysis`).
- Deliberate cap: with only a gap, the overall status cannot exceed
  `PARTIALLY_SUPPORTED` regardless of how small the gap is. This is the flagship
  "technically successful, scientifically insufficient" case and must be enforced by a
  test, not by prose.
- Methodological check: compared state energies must come from a consistent method,
  basis, and geometry.
- Never asserted: device-level TADF performance, or that the molecule "is a TADF emitter".

### 7.3 Transition-state validation

- Claims: the optimized structure is a first-order saddle point of the computed surface;
  the saddle point connects the proposed reactant and product.
- `REQUIRED` converged stationary point with exactly one imaginary frequency at a
  consistent level of theory; `REQUIRED` mode identity **or** pathway connection
  (`normal_mode_inspection` vs `irc | reaction_path_following`, an `ANY_ONE` group).
- Status semantics that must hold: zero imaginary frequencies → `CONTRADICTED` for the
  saddle claim (it is a minimum); more than one → `CONTRADICTED` (higher-order saddle);
  exactly one with no mode or path evidence → never `SUPPORTED`.
- Expert-review boundary: mode correspondence cannot be encoded as a reproducible
  structured assertion, so it must be flagged rather than assumed.
- The protocol's own words, which are the project's epistemics in miniature: one imaginary
  frequency establishes the local Hessian order at the computed stationary point. It does
  not establish the chemical pathway.

## 9. Scientific failure modes and controls

| ID | Failure mode | Control |
| --- | --- | --- |
| F-01 | **Proxy inflation** — a computed proxy read as proof of a stronger claim (small gap ⇒ TADF; one imaginary frequency ⇒ the transition state; non-zero f ⇒ CT) | Epistemic categories on every object; requirement-level assessments; `max_defensible_claim_strength` |
| F-02 | **Unknown becomes false** — absent parser data read as failure | Three-valued logic; `UNKNOWN` propagates; explicit missing-data tests |
| F-03 | **Threshold overreach** — universal numerical cut-offs where none is defensible | No universal cut-offs in code; expert-review boundary instead |
| F-04 | **Method mismatch** — compared values from inconsistent method, basis, or geometry | Methodology validators; requirement-level consistency checks |
| F-05 | **Provenance loss** — externally or LLM-supplied numbers entering as if parsed | `origin` on evidence; provenance mandatory on facts; adapters carry their own producer identity |
| F-06 | **Protocol drift** — a report cannot be reproduced after a protocol edit | Semantic versioning; version recorded in every report and in derived provenance |
| F-07 | **Assertion laundering** — "I checked the mode offline" accepted as verified | `USER_ASSERTION` origin, capped in strength; cannot satisfy `REQUIRED` + `STRONG` |
| F-08 | **Scope creep** — quietly becoming an orchestration or execution tool | Non-goals section is normative; new capabilities require a scope decision |
| F-09 | **Explanation overshoot** — prose claims more than the structure supports | Render from templates driven by structured state; snapshot tests assert status and uncertainty survive rendering |
| F-10 | **Silent defaults** — assuming singlet multiplicity, or reading missing frequencies as converged | Defaults must be explicit and recorded as assumptions, never inferred |

## 10. Minimal dependency set

Runtime: **none.** The core uses only the standard library (`dataclasses`, `enum`,
`pathlib`, `re`, `json`, `datetime`, `argparse`).

Optional extras, added only when the corresponding milestone needs them:

- `qcjudge[cclib]` — `cclib` as an alternative parser backend. BSD-3-Clause, compatible
  with our BSD-3-Clause licence; verify the pinned version's terms before release.
- `qcjudge[dev]` — `pytest`, `ruff`, `mypy`; later `hypothesis` for property tests and
  `pytest-cov`.

Deliberately excluded from the core in V0.1: `numpy`/`pandas` (no array workloads yet),
`pydantic` (frozen dataclasses suffice; revisit only if the serialization boundary becomes
painful), `rdkit`, any LLM SDK, any web framework, any database, any message queue.

Licence note for the adapter seam: Multiwfn is not an OSI-approved open-source project.
The adapter must consume its *exported* text or structured data and must not bundle or
link it. This needs a dependency-and-attribution section before the adapter ships.

## 11. Test strategy

Ordered by how much scientific risk each layer carries:

1. **Domain invariants** — construction rules, three-valued logic, provenance completeness.
   Fast, no I/O.
2. **Protocol graph integrity** — unique IDs, known claim references, dependency
   acyclicity, group symmetry, `implementation_key` resolvable in the validator registry.
3. **The independence property** — for every fixture: `execution = PASS` never implies
   `evidence = SUPPORTED`, and `execution = FAIL` never produces `CONTRADICTED`. This is
   the project's defining invariant and it needs a truth-table, not one example.
4. **Validator units** — convergence, frequency counting, consistency checks, and
   specifically that absent inputs yield `UNKNOWN` rather than `FAIL`.
5. **Parser contract tests** — synthetic ORCA fixtures, including truncated, malformed,
   and mixed-version files. Assert the parser never sets a status and never invents a value.
6. **Scenario matrix** — the acceptance corpus below, run through the real engine.
7. **Golden reports** — JSON output is the stable contract; text rendering gets a small
   number of snapshots that assert uncertainty survives.
8. **Static and structural** — ruff, mypy strict, and the import-boundary test.
9. **CI matrix** — Python 3.12 and 3.13 on Linux, macOS, and Windows.

Non-goals for the test suite: no network access, no quantum-chemistry executables, no
timing-sensitive assertions. Real-world corpora are pulled by a separate, opt-in fetch
script with checksums and are never vendored; see `docs/benchmarks.md` for the sources,
their licences, and the ablation method that generates the evidence-adequacy labels below.

### Acceptance corpus

`TECHNICALLY_SUCCESSFUL != SCIENTIFICALLY_SUFFICIENT` must hold for every row.

| Fixture | Execution | Structural | Evidence | Overall |
| --- | --- | --- | --- | --- |
| CT: TDDFT energies + hole-electron descriptor | PASS | - | complete | SUPPORTED |
| CT: TDDFT energies only, no descriptor | PASS | - | spatial missing | INSUFFICIENT |
| CT: state assignment absent | PASS | - | assignment missing | INSUFFICIENT |
| CT: descriptor supplied below the required strength | PASS | - | present but weak | PARTIALLY_SUPPORTED |
| CT: user asserts the descriptor was computed | PASS | - | assertion only | PARTIALLY_SUPPORTED |
| TADF: ΔEST only, no SOC or kinetics | PASS | - | RISC missing | PARTIALLY_SUPPORTED (capped by design) |
| TADF: ΔEST + SOC | PASS | - | complete | SUPPORTED |
| TADF: states compared at inconsistent methods | PASS | - | expert boundary | REQUIRES_EXPERT_REVIEW |
| TS: exactly one imaginary frequency, no mode or path evidence | PASS | PASS | mode/path missing | PARTIALLY_SUPPORTED |
| TS: zero imaginary frequencies | PASS | FAIL | contradicted | CONTRADICTED |
| TS: multiple imaginary frequencies | PASS | FAIL | contradicted | CONTRADICTED |
| TS: one imaginary frequency + IRC supplied | PASS | PASS | complete via group | SUPPORTED |
| TS: reported mode list is incomplete | PASS | UNKNOWN | not determinable | NOT_ASSESSABLE |
| TS: no frequency calculation at all | PASS | - | never computed | INSUFFICIENT |
| SCF not converged | FAIL | - | - | NOT_ASSESSABLE |
| Optimization not converged | FAIL | - | - | NOT_ASSESSABLE |
| Convergence markers absent entirely | UNKNOWN | - | - | NOT_ASSESSABLE |

Two rows are worth reading together. Zero imaginary frequencies gives `execution = PASS`
with `structure = FAIL`: a converged minimum is a successful calculation. And an incomplete
mode list gives `NOT_ASSESSABLE` rather than `CONTRADICTED`, because a truncated Hessian is
not evidence of anything.

## 13. Decisions and remaining leanings

Settled. These bind the M1 implementation and the acceptance corpus.

| Q | Decision | Consequence |
| --- | --- | --- |
| Q1 | `Hypothesis` is a first-class level: Question to Hypothesis to Claim to Requirement | the report can state "claim A supported, claim B unevidenced, therefore the hypothesis is not established" |
| Q2 | User-asserted evidence is admissible, tagged `USER_ASSERTION`, capped in strength and directness, never satisfying `REQUIRED` + `STRONG` | a user who did inspect a mode is recorded honestly, without that assertion masquerading as verified data |
| Q5 | An unmet `RECOMMENDED` requirement does not cap the overall status; it becomes a reported gap and a recommendation | `SUPPORTED` stays meaningful instead of becoming unreachable in practice |
| Q6 | The TADF protocol is capped at `PARTIALLY_SUPPORTED` when only energetics are available, however small the computed gap | the flagship technically-successful / scientifically-insufficient case, enforced by the acceptance corpus rather than by prose |
| Q9 | A key produced only by arithmetic inherits the absence reason of its sources; it is never reported as `UNSUPPORTED_CONSTRUCT` merely because the reader does not produce it directly | "we cannot compute it because you did not run it" stays a coverage gap (`INSUFFICIENT`), so an omission is never charged to our reader. See D-23 |
| Q10 | A list-valued observation from a file that did not end normally is withheld, not projected | counting imaginary modes from a truncated Hessian cannot invent either `SUPPORTED` or `CONTRADICTED`. Scalars are unaffected: a value like `scf.converged` stands on its own. See D-24 |
| Q11 | A validation scope with no declared check reports `UNKNOWN`, never `PASS` | "not examined" and "examined and found consistent" stop being the same sentence. See D-25 |
| Q12 | Claim, requirement, hypothesis and rule ids must be disjoint within a protocol | trace edges are strings, so a shared id makes a relation unreadable; the collision is now refused at protocol load. See D-26 |

Still on the proposed default and not blocking. Revisit only if they cause rework:

- **Q3** alternatives as explicit `EvidenceGroup(ANY_ONE|ALL)` rather than reciprocal
  per-requirement references.
- **Q4** protocols as typed Python now; any YAML is a compile source and never authoritative.
- **Q7** a per-protocol `max_defensible_claim_strength`, so rendering cannot outrun the structure.
  Half-settled: the declaration reaches the report and both renderers, but it is still prose
  rather than a strength level, so nothing mechanically prevents an overclaim. See D-31, D-32.
- **Q8** the M2 ORCA minimum: software and version, calculation type, method, basis, charge,
  multiplicity, SCF convergence, geometry convergence, frequencies, excited-state energies,
  oscillator strengths, spin expectation — and nothing else until a protocol needs it.

Settled CLI decisions (M3 complete):

- **Q13 — settled.** What does `qcjudge audit` return when the execution axis is `PASS` and the
  evidence axis is `INSUFFICIENT`? **`0`.** An exit code describes the run, not the verdict: the
  report is the deliverable, so any invocation that produced one succeeded, and a caller
  branches on `evidence.overall_status` in `--format json`. `2` means no audit could be
  produced. The implemented adapter lets all three families reach `SUPPORTED` with appropriately
  associated evidence. This keeps "we audited it and the evidence is thin" distinguishable
  from "we could not audit it at all".
- **Q14 — settled.** How does a researcher report a condition only they can observe?
  **`--condition KEY=VALUE` plus `--expert-review REQUIREMENT_ID`.** A condition naming a key a
  protocol declares with `expert_review_when_key` makes that boundary fire; a condition naming
  nothing known is still recorded, so the report shows what the audit was told; and
  `--expert-review` reports a boundary directly. Both refuse an unknown requirement or a
  requirement that declares no boundary, so a typo cannot look like a recorded judgement.
  Neither is evidence: no fact is cited and no requirement is satisfied by it.

## 14. Conventions

- Stable string IDs for graph edges in V0.1; no premature entity framework.
- Protocols are semantically versioned; every report records the version it used.
- Unknown is `None` internally and renders as unknown, never as zero or false.
- `REQUIRES_EXPERT_REVIEW` is a success condition of the design, not an error.
- New scientific capability requires a protocol and tests; it never enters the audit
  engine as a special case.
